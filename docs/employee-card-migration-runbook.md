# 员工办卡结构升级与回退

## 版本和范围

新迁移为 `migrations/postgresql/0005_employee_cards.sql`，只新增9张员工办卡表、索引及六家运营商/八条规则配置；不创建员工、演示卡或实名关联，不改旧表、权限、账号密码和业务数据。0001～0004必须保持原文件及哈希。

员工模块原发布 `71032fb` 接受完整且哈希匹配的v4或v5；后续 `caf5691` 运行时接受合法v4/v5/v6，并按明确的version5核对员工模块。v4时旧业务继续运行，新模块明确显示“结构升级尚未完成”，禁止写入。v5还须通过迁移哈希和全部新表存在性检查才开放。启动过程不会自动执行迁移。

仓库含有0006或更高迁移时，当前 `pg_schema.apply_migrations()` 会应用至文件列表末尾，不能把它当作“仅执行0005”。仅授权员工办卡升级时，使用服务器私有目录中的原 `71032fb` Git字节快照：原样保存 `pg_schema.py` 及其 `migrations/postgresql/0001～0005`，以独立模块名加载原始迁移函数；先核对快照、部署前5文件和数据库历史哈希逐项一致，且当前运行时明确支持合法v5。不得修改 `FILES`、替换运行时模块、转换迁移换行或改写历史哈希来通过校验。已是合法v5/v6时只核验，不重复升级。

## 正式升级条件

以下只在正式服务器已有受控运维环境执行；不把生产连接信息复制到本机，不在聊天、命令日志中打印密码、令牌、环境文件或连接串。先具备现有服务器命令通道和数据库迁移权限；腾讯云CAM拒绝不是新增授权，不更换身份或修改规则绕过。

1. 通过 `systemctl show -p WorkingDirectory --value douyin-board.service` 确认实际代码目录，核对待发布Git提交、新迁移SHA256、正在使用的Python环境和已有服务环境。不要输出环境值。
2. 确认原站健康和就绪，旧4个迁移与数据库历史及原始Git字节哈希一致，不能拿Windows工作副本的不同换行哈希替代。核对当前runtime_control的mode、writer_epoch、restore_generation，保存服务器本地回退收据；不改变代次或登录身份。记录并暂停原同步timer，确认同步服务已终止且MainPID/ControlPID均为0；不能仅凭oneshot的 `is-active` 返回码判断。已有执行或维护收据时停止复核，不盲目重跑覆盖原timer状态。
3. 用现有写入控制进入maintenance，等待在途写事务结束。使用已有受控数据库凭据和 `pg_dump` 把完整业务schema备份到服务器私有目录，文件权限0600；凭据通过已有受保护环境或passfile提供，不放进命令参数。
4. 核对备份成功退出、私有文件权限、流式SHA256、`pg_restore --list`中全部旧表及序列条目，并用 `pg_restore --file=/dev/null` 校验完整解码；这不等于已经做过恢复演练。不上传备份，不在输出中列出业务资料。备份校验未完成就不执行迁移。
5. 在服务器同一受控环境，用原生psycopg连接并显式设置 `search_path=board_candidate,pg_catalog`，调用本次已核对、范围仅到0005的原始迁移函数。再次核对精确v4、maintenance、原表集合无新增、旧数据/ACL/序列指纹及备份SHA；与迁移使用相同advisory锁，确认timer仍暂停、同步服务仍终止。函数核对迁移历史、maintenance、锁超时及事务，失败回滚。不要运行 `cloudbase_prepare.py`、owner初始化或改密码脚本：空库初始化可能改变恢复代次，不属于本次升级。
6. 校验v5迁移行/哈希、9张新表、6个运营商和8条规则；员工、卡关联及申请应为空。核对旧账号、手机卡、设备、员工登录人数和原授权保持，并核对现有运行角色具有新表所需的既定应用访问能力。禁止为了迁移放宽业务人员权限或公网数据库端口。
7. 校验通过后按原控制行身份条件恢复open，保持writer_epoch/restore_generation不变，按原流程重启和检查health/ready，再恢复原timer状态。后端标记须与实际部署代码的 `board_performance.BUILD_ID` 一致；后续代码可有新标记，不能用标记替代数据库版本检查。新接口匿名401且no-store，有权人员读到available=true。
8. 正式页面只读验收员工入口、空台账提示、既有人员候选及权限。员工资料、生日授权和实名归属由有依据的人员逐条确认，不把本机合成记录导入正式环境。

这些步骤依赖服务器现场检查结果，不能把本文当作已经执行的记录。执行收据须分别记录代码版本、备份校验、结构版本和页面结果。

## 回退

迁移执行失败保持maintenance，先检查事务已回滚，再由有权限运维恢复原open状态；不盲目删除表或导入旧业务库。原迁移函数返回后DDL已提交，后置检查失败可能留下v5＋maintenance，此时必须按原收据核对实际结构，不能重跑要求v4的步骤。原控制行和timer收据必须保留，不自动恢复数据库或覆盖并发变化。

升级成功后优先只回退界面或关闭新模块入口，保留新增数据和历史。v5不能直接启动只认识v4的旧运行时：如需回退到旧提交，应保留本轮已验证的v4/v5兼容检查，或使用专门验证的回退构建。不要DROP新表，也不要用旧SQLite库覆盖生产。完整数据库恢复属于另一次明确授权的操作。

仅在尚未合入后续扩展的原 `71032fb` 代码上，已验证的回退构建需保留这4个兼容文件：`pg_schema.py`、`pg_runtime.py`、`cloudbase_runtime.py`和`migrations/postgresql/0005_employee_cards.sql`；这不是当前主线的充分回退集合。回退构建必须重新运行旧业务回归和启动核对，不可在含办公室三未提交资料的原工作区操作。

主线已包含后续模块时，优先只关闭员工入口或回退界面，保留后续代码和已经安装结构的兼容检查。`caf5691` 的 `pg_schema.validate_extensions()` 在v5启动时会导入 `employee_cards.py`，因此还须保留该模块、`employee_card_rules.py`及其既有依赖；不能机械撤销原提交、删除模块后只保留上述四文件，也不能为了撤销员工入口而回退或覆盖其他模块。
