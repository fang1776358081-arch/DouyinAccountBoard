# 员工办卡结构升级与回退

## 版本和范围

新迁移为 `migrations/postgresql/0005_employee_cards.sql`，只新增9张员工办卡表、索引及六家运营商/八条规则配置；不创建员工、演示卡或实名关联，不改旧表、权限、账号密码和业务数据。0001～0004必须保持原文件及哈希。

本次运行时仅接受完整且哈希匹配的v4或v5。v4时旧业务继续运行，新模块明确显示“结构升级尚未完成”，禁止写入。v5还须通过迁移哈希和全部新表存在性检查才开放。启动过程不会自动执行迁移。

## 正式升级条件

以下只在正式服务器已有受控运维环境执行；不把生产连接信息复制到本机，不在聊天、命令日志中打印密码、令牌、环境文件或连接串。先具备现有服务器命令通道和数据库迁移权限；腾讯云CAM拒绝不是新增授权，不更换身份或修改规则绕过。

1. 通过 `systemctl show -p WorkingDirectory --value douyin-board.service` 确认实际代码目录，核对待发布Git提交、新迁移SHA256、正在使用的Python环境和已有服务环境。不要输出环境值。
2. 确认原站健康和就绪，旧4个迁移与已发布哈希一致。核对当前runtime_control的mode、writer_epoch、restore_generation，保存服务器本地回退收据；不改变代次或登录身份。
3. 用现有写入控制进入maintenance，等待在途写事务结束。使用已有受控数据库凭据和 `pg_dump` 把完整业务schema备份到服务器私有目录，文件权限0600；凭据通过已有受保护环境或passfile提供，不放进命令参数。
4. 核对备份成功退出、SHA256、`pg_restore --list`完整性及足够的恢复条件；不上传备份，不在输出中列出业务资料。备份校验未完成就不执行迁移。
5. 在服务器同一受控环境调用已有 `pg_schema.apply_migrations(connection)`。该函数核对迁移历史、maintenance、锁超时及事务；只能从匹配的旧版本前进，失败回滚。不要运行面向空库的owner初始化或改密码脚本。
6. 校验v5迁移行/哈希、9张新表、6个运营商和8条规则；员工、卡关联及申请应为空。核对旧账号、手机卡、设备、员工登录人数和原授权保持，并核对现有运行角色具有新表所需的既定应用访问能力。禁止为了迁移放宽业务人员权限或公网数据库端口。
7. 校验通过后恢复原open状态，保持writer_epoch/restore_generation不变，按原流程重启和检查health/ready。后端发布标记为 `employee-cards-20261102-r1`；新接口匿名401且no-store，有权人员读到available=true。
8. 正式页面只读验收员工入口、空台账提示、既有人员候选及权限。员工资料、生日授权和实名归属由有依据的人员逐条确认，不把本机合成记录导入正式环境。

这些步骤依赖服务器现场检查结果，不能把本文当作已经执行的记录。执行收据须分别记录代码版本、备份校验、结构版本和页面结果。

## 回退

迁移执行失败保持maintenance，先检查事务已回滚，再由有权限运维恢复原open状态；不盲目删除表或导入旧业务库。

升级成功后优先只回退界面或关闭新模块入口，保留新增数据和历史。v5不能直接启动只认识v4的旧运行时：如需回退到旧提交，应保留本轮已验证的v4/v5兼容检查，或使用专门验证的回退构建。不要DROP新表，也不要用旧SQLite库覆盖生产。完整数据库恢复属于另一次明确授权的操作。

在干净的最新main副本中撤销本次功能提交时，明确保留这4个兼容文件：`pg_schema.py`、`pg_runtime.py`、`cloudbase_runtime.py`和`migrations/postgresql/0005_employee_cards.sql`。再运行旧业务回归和启动核对，生成新的回退提交。这样旧界面不读取新模块，但仍能接受已安装的v5，数据与新表保留。不可在含办公室三未提交资料的原工作区操作。
