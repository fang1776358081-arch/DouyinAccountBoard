# 当前服务器多人同时使用计划

版本：1.0  
日期：2026年10月25日  
项目：`F:\AI\FZ\DouyinAccountBoard`  
用途：让大约 50 人在现有腾讯云轻量服务器上打开同一个工作台，查看和修改同一份数据。  
状态：方案已写明，尚未改代码、尚未部署、尚未验收。本文不代替《第一版上线实施计划》，也不表示其中任何任务已经完成。

## 一 要达到的结果

员工用自己的账号进入工作台，只看到管理员分给自己的办公室。发布看板、账号、手机卡、手机设备和养号都是服务器上的同一份资料。同事保存后，其他人屏幕上大约一两秒内只更新那一条。

机器维持现在的配置：2 核、2G 内存、3Mbps 带宽，网站和数据库在同一台。采集保持关闭。目标是 50 人同时开着看板，其中大约 10 人在改单条资料。这个人数是按本方案的传输方式估计的，做完后要用 50 个登录核对，不能把估计写成已经测过。

本文不授权购买更大的机器，不授权把这台电脑上的桌面数据库上传到服务器，不授权开启采集。

## 二 现在为什么带不住

发布看板开着时，每人每 5 秒向服务器要一整份资料，账号、手机卡、设备、养号和发布记录都重新查询、重新下载。50 人大约是每秒 10 次整份读取。3Mbps 和 2G 内存会先满。

保存时如果整页再读一次，还可能读到尚未换新的旧结果。搜索、筛选、养号和批量修改都依赖这一整份数据，不能为了变小而删掉抖音号、手机号、核对情况和养号状态。

## 三 做法

第一次打开，仍然下载这个人有权查看的完整看板。搜索、筛选、养号、手机卡、手机设备和批量修改继续使用这份数据。

之后取消每 5 秒的整份刷新。每个人保持一个等待更新的连接。这个连接只认当前登录的人，等待期间不占用数据库连接。

有人保存成功后，服务器只把改过的那一条发给能看到它的人。发不发，仍按这个人的办公室权限决定，不把整份表交给所有连接共用。看不到该办公室的人收不到这一条。账号换了办公室时，原办公室收到「这条已不在你这里」，新办公室收到这条新资料。

自己保存成功后，页面直接留下服务器返回的这一条，不再为了确认结果而重新下载整份看板。同事的看板上大约一两秒后出现同一条。

编辑框打开时记下当时的版本。别人的更新可以改看板上的那一行，不改这个编辑框里已经记下的版本，也不改编辑框里已经填的内容。

恢复备份或导入整批资料时更换编号。正在打开的页面收到新编号后，整份重新加载一次。仍拿旧编号来保存的请求会被拒绝，不能把恢复前的内容写回去。

导入、导出和上传截图同一时间只做一件，后面的人等待。普通查看和单条保存不进入这个队列。

采集保持关闭，工作台上不再每 5 秒询问采集进度。

桌面壳和网站共用页面。服务器还没有等待更新的接口时，页面继续使用现在的 5 秒整份刷新，避免只更新了页面就把旧桌面壳弄坏。分发给别人的桌面壳应打开服务器网址 `http://42.192.45.194`，使用服务器上的账号和数据，不在对方电脑上自带一份数据库。

## 四 员工使用时会看到什么

员工登录后只看到分给自己的办公室，看不到「子账号与权限」，也看不到其他办公室。

页面第一次打开时载入本办公室的看板，之后停在那里，不会每隔几秒整页重载。同事改了自己能看到的账号，大约一两秒后只有那一行变化。按抖音号、手机号、核对情况和养号状态搜索，仍然可用。

改一条没有别人在改的账号：打开编辑框，保存成功后编辑框关闭，这一行马上是新内容，同事屏幕上也出现这一条。

两个人改不同的账号，各自保存成功。

两个人改同一条账号，先保存的人成功。后保存的人看到「这条资料已被其他人修改，请刷新核对后再保存」。后一次填写的内容不会写入，也不会盖掉先保存的内容。同一条里一个人改备注、另一个人改状态，同样不自动合并，后一次整单拒绝。后保存的人先看过新内容，再重新修改。

编辑框还开着时，别人先保存了这一条。编辑框里仍是打开时的内容，看板那一行变成新内容。这时再点保存，会被拒绝。

点「已发」时，如果同事刚刚标过而自己的画面还没更新，这次点击被拒绝，格子保持同事保存后的结果，不会把对方刚标上的已发取消。

批量修改时，只要其中一条的版本已经变了，这一批都不保存。刷新核对后再重新选择。

别人正在导入、导出或上传截图时，自己要等上一件做完。平时改账号不用等。采集按钮仍在，采集没有开启，不会开始采集。

## 五 多人改同一条时服务器怎么处理

每条资料有一个由当前内容算出的版本。打开编辑框时，页面记下这个版本，并在保存时交给服务器。

服务器一次只处理一个写入。后到的保存先拿到锁，再核对版本。版本已经变了，就拒绝这次保存，数据库保持先保存的人写下的内容。几乎同时点击时也是这个规则，不是两个人都写进去、后写的盖住先写的。

批量修改把选中的每一条都放进同一次核对。任意一条对不上，整批回滚。

这个规则沿用现在的冲突检查，不改成按字段拼接两个人的修改。

## 六 实施顺序

1. 保留现在的看板首次加载。增加一个按登录用户等待的更新接口，等待时不占用数据库连接。接口不存在时，页面维持 5 秒整份刷新。
2. 保存成功并提交之后，只把本次改变的记录交给有权查看的等待连接。自己的保存结果直接更新当前页，不再整份重载。
3. 编辑框继续使用打开时记下的版本。看板上的新行不写入这个版本。
4. 恢复和导入成功后更换编号，旧页面整份重载，旧编号的保存被拒绝。
5. 导入、导出和截图改为同时只做一件。采集关闭时停止采集进度的定时询问。
6. 用下面的验收核对。通过前不把 50 人同时使用写成已经成立。

分发版桌面壳改为打开 `http://42.192.45.194`，与本方案的页面更新分开实施。别人拿到的程序不再启动本地数据库。

## 七 验收

每项都要能重复做出。未做的保持未通过。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| C01 | 50 个有权账号打开看板并停留 | 不再每 5 秒各下载一整份；数据库连接不被这些等待占住 |
| C02 | 一人修改一条账号 | 本人马上看到新内容；同一办公室的其他人大约一两秒内只更新这一条 |
| C03 | 两人同时改不同账号 | 两次都成功，页面各自出现对应的那一条 |
| C04 | 两人改同一条，包括改不同栏目 | 先保存的留下；后保存的被拒绝且未写入；提示核对后再保存 |
| C05 | 编辑框开着时别人先保存 | 编辑框仍是旧内容；再保存被拒绝；看板那一行已是新内容 |
| C06 | 后到的「已发」点击 | 不改变先保存的人写下的发布结果 |
| C07 | 批量中有一条已被别人修改 | 整批不保存 |
| C08 | 员工与另一个办公室 | 收不到那个办公室的更新，也看不到其中的账号 |
| C09 | 账号调整到另一个办公室 | 原办公室不再看到它，新办公室能看到 |
| C10 | 恢复或导入之后用旧页面保存 | 旧页面先整份重载；旧编号保存被拒绝 |
| C11 | 搜索和筛选 | 抖音号、手机号、核对情况、养号状态仍然有效 |
| C12 | 导入、导出或截图同时发起两件 | 第二件等待，第一件完成后才开始 |
| C13 | 旧桌面壳没有更新接口 | 仍能按现在的方式打开和刷新，不出现空白或脚本错误 |

C01 使用测试账号和合成数据，不使用这台电脑上的正式桌面库。

## 八 仍然存在的限制

50 人同时上传截图或下载大表时，3Mbps 会满。这两件事必须排队，不能靠本方案变成同时进行。

50 人挤在同一秒第一次打开时，每人仍要下载自己有权查看的那一份完整看板，第一次会比之后的修改慢。

总管理员查看全部办公室时，第一次下载仍然是整份。本方案去掉的是之后的重复下载，不是管理员第一次打开的体积。

服务器上目前还没有拿来给大家一起改的那份业务资料。本文不包含把这台电脑里的桌面数据上传到服务器。没有这份数据时，大家打开的是同一个空工作台。

员工账号要由总管理员单独创建，并分给办公室。没有分到办公室的员工看不到业务资料。

这台机器仍然不能打开采集。50 人和 75 人的原负载验收、两小时耐久、更大带宽和独立数据库，仍以《第一版上线实施计划》为准，不因本文而视为完成。
